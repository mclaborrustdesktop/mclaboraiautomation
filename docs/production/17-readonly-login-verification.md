# 17. The strictly read-only synchronization account: design, rehearsal on the copy, verification on the live server

Date: 2026-11-26. Nothing in this page touched the live server. The rehearsal ran against the restored copy on the
development PC with the copy's restricted login; it read metadata only and changed nothing.

## 1. What the account is

| Item | Value |
|---|---|
| Login | `mclabor_web_read`, SQL authentication (the office PC and the live server share no Windows domain), `CHECK_POLICY = ON`, default database `McLabor` |
| Database user / role | user `mclabor_web_read`, member of **one** role, `mclabor_web_readonly`; in no built-in role (not db_datareader, not db_datawriter, not db_owner) |
| Granted | `SELECT` on **288 named columns of 33 tables** (`tools/prod-check/required_schema.json`), nothing else |
| Explicitly refused (STEP 3b, new) | database-level `DENY INSERT, UPDATE, DELETE, EXECUTE, ALTER, REFERENCES, CREATE TABLE, CREATE VIEW, CREATE PROCEDURE, CREATE FUNCTION, CREATE SCHEMA, CREATE TYPE, ALTER ANY SCHEMA, ALTER ANY USER, ALTER ANY ROLE, TAKE OWNERSHIP, BACKUP DATABASE, BACKUP LOG`; column-level `DENY SELECT` on the 17 sensitive columns (SSN, bank, date of birth, citizenship, I-9, W-4, sex, race, dependents, staff passwords); server-level `DENY VIEW ANY DATABASE` |
| Why DENY | In SQL Server a DENY always beats a GRANT, including a GRANT that arrives later through a role or through `public`. So the account stays read-only even if someone later adds it to db_datawriter or grants EXECUTE on a procedure. `CONTROL` is deliberately not denied: denying it would deny SELECT too. |
| How the other verbs are covered | MERGE needs INSERT/UPDATE/DELETE (denied). DROP and TRUNCATE need ALTER on the object or schema (ALTER denied at database level, which cascades). BULK INSERT needs INSERT plus a server permission (denied / not granted). Stored procedures and functions, including write-capable ones that run as their owner, need EXECUTE (denied). Impersonation: no IMPERSONATE grant exists. Ownership chaining: the role owns nothing. |
| Scripts | `tools/prod-check/proposed-grants-production.sql` (live server), `proposed-grants.sql` (restored copy), `verify-readonly-login.sql` (read-only effective-permission report), all generated by `build_required_schema.py` from the application's models; tests in `backend/tests/test_prodcheck.py` |

The synchronization agent uses this login only (`PRODUCTION_DB_USER=mclabor_web_read`, password in Windows DPAPI on
the office PC), connects with encryption and `ApplicationIntent=ReadOnly`, refuses any server other than
`PRODUCTION_DB_EXPECTED_SERVER_NAME`, and runs SELECT statements only (the engine's statement guard). It never uses
an administrator credential; administrators run the one-time scripts themselves in Management Studio.

## 2. Rehearsal on the restored copy (2026-11-26, read-only)

`tools/prod-check/check_readonly.py` against the copy with the copy's `mclabor_web_read` login (created on 2026-11-20
from the previous version of the grant script, i.e. without STEP 3b). Checks run as that login, metadata only:

| Check | Result |
|---|---|
| Server identifies itself as the expected copy; connected as `mclabor_web_read`; encrypted | OK |
| Fixed server roles (sysadmin, securityadmin, serveradmin, setupadmin, processadmin, diskadmin, dbcreator, bulkadmin) | none |
| Database-wide INSERT / UPDATE / DELETE / ALTER / EXECUTE / CONTROL | none |
| INSERT / UPDATE / DELETE / ALTER on **any** table or view of the database (not only the 33) | none |
| Readable columns on the approved tables | exactly 288 |
| Sensitive columns readable | none of the 17 |
| Tables/views visible | 33 (the approved ones) |
| Schema compatibility of the 33 tables / 288 columns | OK |
| **Executable routines** | **FAIL: 7** - `dbo.sp_creatediagram`, `sp_alterdiagram`, `sp_dropdiagram`, `sp_renamediagram`, `sp_helpdiagrams`, `sp_helpdiagramdefinition`, `fn_diagramobjects`, all with `GRANT EXECUTE` to `public` |
| VIEW ANY DATABASE | WARN: can list the server's databases |

The 7 routines are the database-diagram helpers that SQL Server Management Studio installs in a database the first
time someone draws a diagram, granting them to `public`. Three of them write (they create, alter and drop rows in
`dbo.sysdiagrams`, running as the database owner). They cannot touch business tables, but they are exactly the kind
of inherited, write-capable right the account must not have. The live server very likely has the same seven.

Both findings are closed by the regenerated scripts: STEP 3b (`DENY EXECUTE` at database level beats `public`'s
GRANT) and STEP 1 (`DENY VIEW ANY DATABASE`). They are **not yet applied to the copy**: that needs the owner's
go-ahead for two statements run by the copy's administrator (this PC's Windows account):
```
USE [McLabor]; DENY INSERT, UPDATE, DELETE, EXECUTE, ALTER, REFERENCES, CREATE TABLE, CREATE VIEW, CREATE PROCEDURE, CREATE FUNCTION, CREATE SCHEMA, CREATE TYPE, ALTER ANY SCHEMA, ALTER ANY USER, ALTER ANY ROLE, TAKE OWNERSHIP, BACKUP DATABASE, BACKUP LOG ON DATABASE::[McLabor] TO [mclabor_web_readonly];
USE [master];  DENY VIEW ANY DATABASE TO [mclabor_web_read];
```
(plus the two column DENYs from STEP 3b), after which `check_readonly.py` must report READY with 0 problems.

## 3. Procedure for the live server (administrator, after the owner's approval)

1. Confirm the server name with `SELECT SERVERPROPERTY('ServerName')`; in `proposed-grants-production.sql` replace the
   `LIVE-HOST` placeholder with it (the script stops on any other server). Replace the password placeholder with a
   generated password of 16 or more characters; never e-mail or paste it.
2. Run `proposed-grants-production.sql` in Management Studio as a sysadmin. It creates one login, one user, one role,
   288 column grants and the refusals. It changes no data, no setting and no existing permission. Safe to rerun.
   STEP 4 prints: 288 SELECT column permissions on 33 tables; 18 database DENYs and 17 column DENYs; no unexpected role.
3. Run `verify-readonly-login.sql` (read-only; it impersonates the login with `EXECUTE AS LOGIN` and reverts). Expected:
   every server role 0; database role `mclabor_web_readonly` only; database permissions `CONNECT` only; server
   permissions `CONNECT SQL` only; **0** rows of write rights on any table or view; **0** executable routines; 288
   readable approved columns; every sensitive column 0; **0** readable unapproved tables; visible databases
   master, tempdb, McLabor. Send the output to the owner (it contains no data and no password).
4. On the office PC, with `tools/prod-check/prodcheck.env.production` (AUTH=sql, USER=mclabor_web_read, the expected
   server name): `check_readonly.py` must end with READY, 0 problems, 0 warnings. The password is typed at the hidden
   prompt; the report file contains none.
5. Store the password for the agent with `tools/sync/store-sync-secrets.ps1` (Windows DPAPI, the account that runs the
   scheduled task). Only then the first **dry run** (`run-sync.ps1 -DryRun`), watched by the owner.

## 4. Remaining risks after the account is verified

| Risk | Mitigation in place | Still open |
|---|---|---|
| The password is a single secret that reads all approved business data | DPAPI storage bound to one Windows account on one PC; TLS; `CHECK_POLICY` (lockout and complexity from Windows policy); the login can reach nothing else on the server | rotate it on a schedule (quarterly) and immediately if the office PC changes hands; enable failed-login auditing on the server |
| Other `public` grants on the live server that the copy does not have | `verify-readonly-login.sql` sections 5, 6 and 9 list anything readable, writable or executable beyond the approved list; the DENYs neutralise the write and execute cases | an unexpected readable table would be a **grant to public on the live server**, to be removed by the administrator before the first run |
| Column list drift: a sensitive column added to an approved table later | the agent sends only the columns in `required_schema.json`; the cloud side refuses any other column (422); the DENYs stay | review the list when the Access application changes |
| The Access application's own SQL login (`mclabor`, password inside the Access files, found during the location findings) | out of scope of the website; it is the office's existing practice | the administrator should know it exists; it is the real weak point on that server, not the new read-only login |
| Server-level: `CONNECT SQL` to the instance from the office LAN | the login has no server role, no VIEW ANY DATABASE, no IMPERSONATE | restrict the SQL port to the office LAN in the server's firewall (already the case for the live server per docs/production/15) |
| Human error: an administrator runs the staging-copy script on the live server or vice versa | both scripts stop unless `SERVERPROPERTY('ServerName')` matches their own target | none |

## 5. Approval needed before the first synchronization

1. Owner: apply STEP 3b and the server DENY to the **restored copy** (section 2), then rerun the check to see READY.
2. Owner: approve running `proposed-grants-production.sql` and `verify-readonly-login.sql` on the live server by the
   client's administrator (section 3, steps 1-3) and send back the verification output.
3. After step 4 of section 3 says READY: approve the first dry run. The scheduled task comes later and separately.
