# PostgreSQL schema for the MC Labor database

Generated by `backend/app/pgschema.py` from the client's SQL Server structure export (`docs/schema`). Regenerate
after a change to the export:

```
cd backend
.venv\Scripts\python.exe -m app.pgschema write          -> deploy/railway/postgres/{schema,indexes,trigram-indexes,constraints}.sql
```

| File | What | When to apply |
|---|---|---|
| `schema.sql` | 288 tables (every `tbl*`, the `Web*` tables, `SettingsBE`), 3,328 columns with PostgreSQL types, primary keys inferred from the McLabor naming rule, identity keys that also accept explicit ids, 252 foreign keys (`NOT VALID`: new rows are checked, migrated rows are validated afterwards) | once, on an empty database |
| `indexes.sql` | an index on every foreign-key column plus the search indexes the website's queries use | any time |
| `trigram-indexes.sql` | `pg_trgm` indexes for word searches (`ILIKE`); needs the contrib extension, which Railway's PostgreSQL has | after `indexes.sql`; optional |
| `constraints.sql` | business rules as database constraints: hours 0-24, rates not negative, names not blank, end date not before start date, one week per worker and job (placeholders excepted), one `tblEmployeeB` row per employee, unique staff initials | after the migrated data has been checked (a legacy row that breaks a rule would stop the ALTER); the website enforces the same rules itself |

Apply from this PC to a Railway database (the public connection URL from the Postgres service, TLS):

```
.venv\Scripts\python.exe -m app.pgschema apply "postgresql://user:pw@host:port/railway?sslmode=require" --indexes --constraints
.venv\Scripts\python.exe -m app.synthdb "postgresql://user:pw@host:port/railway?sslmode=require" 0.2 --fill-existing
```

`apply` refuses a database that already has any of the tables and the office servers as hosts; `synthdb` refuses a
database that is not empty and the office servers, and resets the identity sequences after loading its explicit ids.

## Migration (later, with the owner's approval; nothing of it has been run)

1. `apply` the schema on the production database (empty), `indexes.sql` included, `constraints.sql` not yet.
2. Copy the rows table by table from a RESTORED COPY of the SQL Server backup (never from LIVE-HOST live), in
   foreign-key order, with explicit ids; then `reset_sequences`.
3. Validate the foreign keys (`ALTER TABLE ... VALIDATE CONSTRAINT`), fix or record what fails, apply `constraints.sql`.
4. Row counts and checksums of the four main tables against the copy; the website's read-only smoke tests.
The copy tool itself is written at that stage, against the restored copy on DEV-PC, once step 1 of
`docs/cloud/12-railway-plan.md` is approved.
